# C ABI (`persia-ffi`)

**Design only.** There is no `persia-ffi` crate, no header, and no symbol to call. The shapes below are the
contract [ADR-0018](../adr/0018-embedded-sdk-bindings.md) reserves. Names are illustrative until the crate
exists; the rules (ownership, errors, threads, panics) are the decision.

The ABI wraps the Rust facade that ROADMAP M10 will put in `persia`. Today that facade is
[four lines](https://github.com/tomiok/persiaDB/blob/main/crates/persia/src/lib.rs#L1-L4).
Functions appear in the header only after the matching Rust method exists. A header full of symbols that
return `PERSIA_UNSUPPORTED` is not a milestone.

## Library

| Artifact | Crate type | Consumer |
|---|---|---|
| `libpersia_ffi.rlib` | `lib` | `sdk/node` (N-API), Rust tests |
| `libpersia.a` | `staticlib` | Go cgo |
| `libpersia.so` / `libpersia.dylib` / `persia.dll` | `cdylib` | Optional. Not the first Go path (static linking keeps one binary). |

The crate depends only on `persia`. It does not depend on `persia-engine` or `persia-storage` directly:
the dependency arrow stays `persia-ffi` → `persia`, matching the downward rule. When the crate is added,
[`ALLOWED`](https://github.com/tomiok/persiaDB/blob/main/xtask/src/check_deps.rs#L23-L40) gains that one edge.

The C header is `crates/persia-ffi/include/persia.h`, generated by a future `cargo xtask ffi-header`
(cbindgen as a tooling-only dependency of `xtask`) and committed. CI fails if regeneration changes it.
No `build.rs` (ADR-0003).

Symbols are `extern "C"`, prefixed `persia_`. The header defines `PERSIA_ABI_MAJOR` and
`PERSIA_ABI_MINOR`. `persia_abi_version` returns them. Additive functions and fields bump the minor.
Removing a function, changing a struct layout, or renumbering an error code bumps the major. Until format
v1.0 the major may bump on every release (SPEC §15, [distribution](./distribution.md)).

## Two layers inside the crate

```
persia_ffi::api     safe Rust. Takes Rust strings and bytes, returns Result.
                    This is what N-API calls.
persia_ffi::c       extern "C" wrappers. The only module allowed to use unsafe.
                    Added to UNSAFE_ALLOWED (xtask/src/repo_checks.rs) with the crate.
```

`unsafe` is pointer dereference and slice construction from a foreign `(ptr, len)`. A `// SAFETY:` comment
states that the pointer is non-null (already checked), the length is the caller's, and the memory is
readable for this call and not retained. The crate root is `#![deny(unsafe_code)]`, the same pattern as
[`persia-storage`](https://github.com/tomiok/persiaDB/blob/main/crates/persia-storage/src/lib.rs#L4-L5)
after ADR-0017. The allowed-file list today is
[`UNSAFE_ALLOWED`](https://github.com/tomiok/persiaDB/blob/main/xtask/src/repo_checks.rs#L235-L240).

The safe layer is what tests call. The C wrappers are tested by a Rust test that links the staticlib or
calls the exports directly, with null pointers, truncated lengths, and a panic injection hook behind
`cfg(test)`.

## Handles

Opaque heap objects. The header exposes them as incomplete struct types. Callers hold a pointer and never
see the fields.

| Handle | Owns | Closed by |
|---|---|---|
| `persia_db` | The open database: file lock, background flush and merge once those exist (ROADMAP 10.2.3) | `persia_db_close` |
| `persia_collection` | A collection on that database. Holds the db alive. | `persia_collection_close` |
| `persia_blob_reader` | A pull reader for one blob range | `persia_blob_reader_close` |
| `persia_error` | One error value | `persia_error_free` |
| `persia_bytes` | A Rust-allocated buffer returned to the caller | `persia_bytes_free` |

Rules:

- A null handle argument returns `PERSIA_INVALID_ARGUMENT` and does not crash.
- `persia_db_close` on a database that still has open collection or blob-reader handles returns
  `PERSIA_BUSY` and leaves it open. The caller closes children first. Go's `defer` and TypeScript's
  `await using` / explicit `close()` are what make this bearable; a finalizer is only a backstop and is
  not the contract (Go finalizers are not prompt).
- Close waits until in-flight calls on that handle finish, then frees. A call that arrives after close
  has started gets `PERSIA_CLOSED`. Close from inside a call is not possible in the first ABI because
  there are no callbacks.
- Use-after-free is a caller bug. The allocation starts with a magic and a generation so a stale pointer
  whose memory has not been reused returns `PERSIA_INVALID_ARGUMENT`. That check is best-effort. It is
  not a security boundary.
- Handles are not movable across processes and not serializable. A Node `worker_threads` transfer list
  cannot carry one. Each worker opens its own database.

Collection handles keep the database alive so a caller who closes the `Db` wrapper in the wrong order
gets `PERSIA_BUSY` rather than a dangling pointer. They do not create a second writer lock.

## Memory

Caller-owned input (`path`, JSON, ids) is borrowed for the duration of the call. The core copies whatever
it stores (the memtable, the WAL). After the function returns, the caller may reuse or free the buffer.
The C side does not retain the pointer. That is what makes the call legal under cgo's pointer rules: a Go
pointer passed to C is not stored after the call.

Returned bytes are allocated by the Rust allocator. The caller frees them with `persia_bytes_free` or
`persia_error_free`. `free`, `C.free`, and `delete` are the wrong functions. The Go and TypeScript
packages are the only code that should call the free functions; application code sees a Go string or a
`Uint8Array`.

`persia_bytes` is `{ uint8_t *ptr; size_t len; }`. `len` is the payload length. The buffer is also
terminated with a zero byte one past `len`, so C can print a string, and `len` does not include that
byte. Interior zeros are allowed in blob bytes and forbidden in strings the API defines as text (paths,
ids, JSON). A text buffer with an interior zero is `PERSIA_INVALID_ARGUMENT`.

Outputs are written through pointer out-parameters. On failure, handle out-parameters are set to null and
any partially allocated result is freed inside the wrapper. On success, the error out-parameter is set to
null.

## Errors

Every export returns a `persia_status` (`int32`, `0` is success) and, if the caller passed a non-null
`persia_error **`, fills it on failure. The status and the error's code are the same number. The message
is human-readable, not stable, and borrowed from the `persia_error` until `persia_error_free`.

There is no thread-local "last error". Goroutines move between OS threads, and a thread-local would
report the wrong call.

| Code | Name | When | Closest core type today |
|---|---|---|---|
| 0 | `PERSIA_OK` | Success | — |
| 1 | `PERSIA_NOT_FOUND` | Missing document, collection, or blob | `persia_storage::ErrorKind::NotFound` ([error.rs L136–L151](https://github.com/tomiok/persiaDB/blob/main/crates/persia-storage/src/error.rs#L136-L151)) |
| 2 | `PERSIA_ALREADY_EXISTS` | Create of a database or collection that is already there | Container create ([path.rs](https://github.com/tomiok/persiaDB/blob/main/crates/persia-storage/src/container/path.rs)); `PutOutcome::AlreadyExists` is a storage primitive, not this code |
| 3 | `PERSIA_CONFLICT` | Second writer, or a lost lease once leases exist (SPEC §8.4, §11.3) | `ErrorKind::Conflict` exists for storage and is not yet returned by a database open |
| 4 | `PERSIA_INVALID_ARGUMENT` | Null, bad UTF-8, schema rejection, limit exceeded (SPEC §17) | Caller errors on the format reader (`OutOfBounds`, `InvalidInputLen`, [error.rs L23–L25](https://github.com/tomiok/persiaDB/blob/main/crates/persia-format/src/error.rs#L23-L25)) |
| 5 | `PERSIA_CORRUPT` | Bytes on disk or from a peer failed a checksum or a format rule | `Error::Corrupt` / `CorruptBlock`; storage `ErrorKind::Corrupt` |
| 6 | `PERSIA_UNSUPPORTED` | `format_major` or an incompat flag this build does not read (SPEC §15) | `Error::Unsupported` ([header.rs L15–L21](https://github.com/tomiok/persiaDB/blob/main/crates/persia-format/src/header.rs#L15-L21)) |
| 7 | `PERSIA_IO` | Filesystem or network failure that is not a conflict | `ErrorKind::Io` |
| 8 | `PERSIA_TRANSIENT` | Retryable storage failure (SPEC §10.1). Rare in embedded local opens; present for URL opens. | `ErrorKind::Transient`, the only retryable storage kind |
| 9 | `PERSIA_BUSY` | Close while children are open | New at the ABI. Not a storage kind. |
| 10 | `PERSIA_PANIC` | A Rust panic was caught. The handle is poisoned. | Must not happen on hostile input (SPEC §17). Means a bug. |
| 11 | `PERSIA_CLOSED` | Call after close | New at the ABI. |
| 12 | `PERSIA_LIMIT` | A SPEC §17 limit: doc size, field count, query terms, fuzzy expansions, result window | Not a type yet. 10.1.5 assigns it. |

Codes are append-only within an ABI major. The Rust error type from 10.1.5 is the source of the mapping;
this table is the floor the ABI will not shrink. Storage kinds that are an internal detail (a short read
inside the container) surface as `PERSIA_CORRUPT` or `PERSIA_IO`, not as new public codes, unless 10.1.5
makes them distinct.

`PERSIA_TRANSIENT` is the only code a caller should retry blindly. The Go and TypeScript packages do not
retry it themselves in the embedded SDK: a local `put` that failed may have been applied or not, and the
core's own retry policy already covers `put_if_absent` inside the storage layer
([storage.rs L50–L58](https://github.com/tomiok/persiaDB/blob/main/crates/persia-storage/src/storage.rs#L50-L58)).
Retrying a search is safe. Retrying a put is the caller's decision.

## Panics

Library code must not panic on bytes from disk, the network, or the caller
([format error.rs L1–L7](https://github.com/tomiok/persiaDB/blob/main/crates/persia-format/src/error.rs#L1-L7)).
The ABI still assumes a bug can panic.

- Every export wraps the body in `catch_unwind`.
- The crate is built with unwinding panics. `panic = "abort"` is forbidden for this crate: abort would
  kill the Go or Node process on a bug the binding is supposed to report.
- A caught panic becomes `PERSIA_PANIC`. The message is the panic payload when it is a `String` or
  `&str`, otherwise `"panic"`.
- The `persia_db` is poisoned. Later calls on it or its collections return `PERSIA_PANIC` until close.
  Close still runs, so the writer lock is dropped. Committed data stays under the core's crash rules;
  the binding does not keep writing after a panic because the memtable may be half-updated.
- Poison is per database handle, not process-wide.

What `catch_unwind` does not cover, and what the SDK docs must say in the first screen of the Go and
TypeScript readmes: a fault on a mapped page raises `SIGBUS` on Unix and `EXCEPTION_IN_PAGE_ERROR` on
Windows and ends the process
([mmap.rs L1–L8](https://github.com/tomiok/persiaDB/blob/main/crates/persia-format/src/mmap.rs#L1-L8),
ADR-0010). Mapped reads are opt-in (ADR-0017). The default read path is `pread`. The binding does not
install a signal handler. Go's runtime and a Rust library share the process; if mapped reads are turned
on, that interaction is tested on each OS before the option is exposed, and the test is allowed to
conclude the option stays off for cgo.

## Threads

The planned Rust handles are `Send` and `Sync` (ROADMAP 10.2.1). The ABI matches that.

- Search, get, and blob reads may run concurrently on one database, including from several OS threads.
  Each call sees one manifest snapshot (SPEC §8.4).
- `put`, `delete`, `put_batch`, and `commit` take a writer mutex inside the ABI so two threads in one
  process cannot interleave a memtable update. They are ordered, not transactional: SPEC §1.2 excludes
  multi-document transactions. A `put_batch` is one call and holds the mutex for the whole call.
- A second **process** opening the same path for write fails with `PERSIA_CONFLICT` (SPEC §8.4: the
  writer lock fails fast). A second handle in the same process also fails, rather than aliasing the
  first. Readers may open the path alongside the writer.
- The caller does not hold a collection lock across calls. Locking is inside the call.
- Background flush and merge threads belong to the core (ROADMAP 10.2.3). `persia_db_close` asks them to
  stop and waits. The ABI does not expose their handles.

Read-your-writes (SPEC §8.2–§8.4, ROADMAP 10.2.2): a `put` that has returned is visible to a `search`
that starts afterwards on that database, including from another thread, before `commit`. `commit` is
durability and a published manifest, not the moment the write becomes searchable. The memtable is
specified to be searchable as soon as `put` returns. That behavior is the core's; the ABI does not buffer
a second copy.

## Calls

Illustrative. Each function returns `persia_status` and takes `persia_error **err` (nullable). Lengths
are byte lengths. Strings are UTF-8.

### Open and collections

```c
/* ILLUSTRATIVE — not a header in the tree. */
persia_status persia_db_open(
    const uint8_t *path, size_t path_len,
    const persia_open_options *opts, /* nullable: defaults */
    persia_db **out,
    persia_error **err);

persia_status persia_db_close(persia_db *db, persia_error **err);

persia_status persia_db_create_collection(
    persia_db *db,
    const uint8_t *schema_json, size_t schema_len,
    persia_collection **out,
    persia_error **err);

persia_status persia_db_open_collection(
    persia_db *db,
    const uint8_t *name, size_t name_len,
    persia_collection **out,
    persia_error **err);

persia_status persia_db_drop_collection(
    persia_db *db,
    const uint8_t *name, size_t name_len,
    persia_error **err);

persia_status persia_collection_close(persia_collection *c, persia_error **err);

persia_status persia_collection_schema(
    persia_collection *c, persia_bytes *out_json, persia_error **err);
```

`persia_open_options` begins with `uint32_t size` set to `sizeof(persia_open_options)` by the caller, the
usual way to append fields without breaking an old caller. Zero-initialized fields mean "default". The
first version carries `flags` (`PERSIA_OPEN_CREATE`, `PERSIA_OPEN_READ_ONLY`) and nothing else. Knobs from
SPEC §14 (`memtable_bytes`, `fsync_policy`, `relax.*`, mapped reads) are added when `OpenOptions` in Rust
has them (ROADMAP 10.1.1), at the end of the struct, with a minor ABI bump.

`schema_json` is the collection definition in SPEC §6.2. The core parses it. Unknown fields follow that
section: the schema is declared at creation; adding a field later is allowed; changing a field's type is
not. The ABI does not invent a parallel schema language.

### Documents

```c
persia_status persia_collection_put(
    persia_collection *c,
    const uint8_t *doc_json, size_t doc_len,
    persia_error **err);

persia_status persia_collection_put_batch(
    persia_collection *c,
    const uint8_t *docs_json, size_t docs_len, /* one JSON array */
    persia_error **err);

persia_status persia_collection_delete(
    persia_collection *c,
    const uint8_t *id, size_t id_len,
    persia_error **err);

persia_status persia_collection_get(
    persia_collection *c,
    const uint8_t *id, size_t id_len,
    persia_bytes *out_json,
    persia_error **err);

persia_status persia_collection_commit(persia_collection *c, persia_error **err);
```

`put` is an upsert by `id` (SPEC §8.3). Update is the same call. Delete writes a tombstone; it does not
rewrite a segment.

`get` of a missing id is `PERSIA_NOT_FOUND`. It is not an empty document.

`commit` publishes a manifest (SPEC §8.2, §4.5). Where the method sits if the Rust API puts it on `Db` is
an open question in the [index](./README.md). The symbol follows Rust.

`put_batch`'s atomicity is not specified (SPEC §8.1). The ABI exposes one call so the core can define it
once. The JSON array is one buffer so the cgo call is one crossing, not one crossing per document.

Document JSON is an object with a string `id` (at most 512 bytes, SPEC §6.1) and the schema's fields.
The core stores CBOR (SPEC §6.4). Unknown fields are rejected when the collection is strict, which is the
default. Field types are `text`, `keyword`, `i64`, `f64`, `bool`, `datetime`, `stored`. The JSON spelling
of `datetime` is open (index, question 4). `i64` is a JSON integer; a fractional JSON number for an `i64`
field is `PERSIA_INVALID_ARGUMENT`. `f64` is a JSON number.

There is no struct layout for documents in C. Generics do not cross this boundary (ADR-0018).

### Search

```c
persia_status persia_collection_search(
    persia_collection *c,
    const uint8_t *query_json, size_t query_len,
    persia_bytes *out_json,
    persia_error **err);
```

One call, one page. The query object is SPEC §7.1: `q`, `fields`, `filter`, `sort`, `limit`, `offset` or
`search_after`, `facets`, `relax`, `explain`. A string query in Go or TypeScript is the language package
building `{ "q": "..." }` with the collection's defaults.

The response JSON is a proposal until 10.1.3 names the Rust type. It has to be able to carry what the SPEC
already requires:

```json
{
  "hits": [
    {
      "id": "sku-1",
      "score": 1.23,
      "fields": { "title": "Running shoes", "brand": "nike" },
      "blob": null
    }
  ],
  "facets": { "brand": [{ "value": "nike", "count": 4 }] },
  "relaxation": {
    "level": "fuzzy",
    "applied": ["fuzzy"],
    "original": "runing",
    "effective": "running",
    "corrected": { "runing": "running" }
  },
  "manifest_seq": 3
}
```

`relaxation` is SPEC §7.6, including `truncated` when the budget stops the cascade. Filters are not
relaxed unless the query asks (`relax.filters = "last_resort"`). `explain` stays absent until the core
implements SPEC §7.7, which is post-MVP. `blob` on a hit is the `BlobRef` once 9.4.3 includes it; the
text form of the id is 64 lowercase hex characters
([`BlobId`](https://github.com/tomiok/persiaDB/blob/main/crates/persia-format/src/blob.rs#L19-L43)).
`manifest_seq` lets a caller log which snapshot answered. Embedded search does not take a `min_seq`:
the caller is in-process and already has read-your-writes. The server's `min_seq` (SPEC §12.2) stays a
network-client concern.

An empty hit list is success. Relaxation tries to avoid it (default `min_results` is 1) and can still
return empty when the fallback is `none` or the budget runs out. Empty is not an error.

Pagination is `offset` / `limit` or, preferably, `search_after` (SPEC §7.4). The ABI has no search
iterator and no cursor object that borrows the database. The language packages may loop by passing the
last hit's cursor into the next query. Pages are separate calls and may observe a commit that landed
between them. A cursor that a merge has invalidated returns the core's error unchanged.

### Blobs

Blocked on M9 and on SPEC §18.8 (the id is the SHA-256 of the bytes, which is known only after the last
byte). The ABI does not guess the staging scheme.

When the core has `put_blob` / `get_blob_range` (SPEC §9.6, ROADMAP 9.4.2, 10.1.3):

```c
persia_status persia_collection_put_blob(
    persia_collection *c,
    const uint8_t *bytes, size_t len,
    const uint8_t *mime, size_t mime_len,
    persia_bytes *out_ref_json,
    persia_error **err);

persia_status persia_blob_reader_open(
    persia_collection *c,
    const uint8_t *blob_id_hex, size_t id_len,
    uint64_t offset, uint64_t len, /* len 0 means "through the end" */
    persia_blob_reader **out,
    persia_error **err);

persia_status persia_blob_reader_read(
    persia_blob_reader *r,
    uint8_t *buf, size_t buf_len, /* caller-allocated */
    size_t *out_n,                /* 0 means EOF */
    persia_error **err);
```

`read` fills a caller buffer. It does not call back into Go or JavaScript. That keeps cgo pointer rules
and the N-API event loop simple: the host pulls. A convenience `put_blob_path` can be added if the Rust
API grows `Blob::from_path` (SPEC §9.6); it is not required for the first blob slice, and a path the
process should not read is the same trust decision as any other path open.

`put` of a document that references a blob stays two steps in the order SPEC §9.5 requires: blob durable,
then the document commit. The language packages expose a helper that does those two steps. The ABI does
not fuse them into a third write path.

## JSON at the boundary, in one place

The language packages may accept structs, maps, or typed objects. They encode UTF-8 JSON and decode the
JSON the ABI returns. They do not talk CBOR. CBOR is the on-disk document encoding (SPEC §6.4), inside
the core.

Schema, document, query, and response JSON are versioned with the ABI minor. An additive field is a
minor bump. The packages ignore unknown response fields so a newer core can add one without breaking an
older package that was promised that minor... which, before v1.0, it is not promised. The ignore rule is
still the one to write, so the post-1.0 behavior is not a rewrite.

## What this ABI deliberately leaves out

- Callbacks and function pointers, in either direction.
- A streaming search iterator.
- A transaction begin/rollback. There is no such operation (SPEC §1.2).
- Thread, runtime, or allocator replacement. The Rust allocator inside the staticlib is the one that
  frees `persia_bytes`.
- Statistics and admin RPCs. Those are server surface (SPEC §12.2) until the Rust API grows them.
- Anything that is still an open question in SPEC §18, except by passing through whatever the core decides.
