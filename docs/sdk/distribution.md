# Distribution, versions, and tests

**Design only.** No package is published, no CI job builds an SDK, and the compatibility table does not
exist yet. This file is the policy those jobs will follow. The binding decision is
[ADR-0018](../adr/0018-embedded-sdk-bindings.md).

## Three version numbers

They move independently. Collapsing them into one number is how a file-format break gets mistaken for
an npm break, or the other way around.

| Number | What it versions | Who bumps it | Stability today |
|---|---|---|---|
| File format `format_major.minor` | Bytes in a `.persia` file (SPEC §15) | A format change, with the four-step discipline: SPEC, version or flag, ADR, golden fixture | `1.0`, unstable until the v1.0 release. [`FORMAT_MAJOR` is 1 and `FORMAT_MINOR` is 0](https://github.com/tomiok/persiaDB/blob/main/crates/persia-format/src/header.rs#L15-L21). No compatibility promise across releases. |
| C ABI `PERSIA_ABI_MAJOR.MINOR` | Symbols, struct layout, error code numbers, JSON fields the languages share | A breaking change to [c-abi.md](./c-abi.md) | Will start at `0.1` with the crate. Major may break on every pre-1.0 release. |
| Language package | The Go module and the npm packages, semver | A breaking change to the Go or TypeScript API in [go.md](./go.md) / [typescript.md](./typescript.md) | `0.x` until the format is frozen and the API has shipped. `0.x` may break. |

A binding release records the core git revision it was built from and the ABI major it exports. The
file format it can open is exactly the format that core can open. The SDK does not carry its own
decoder.

An unknown `format_major` or an unknown incompat flag fails at open with `unsupported`
(SPEC §4.2, SPEC §15). The SDK surfaces that code and does not try to migrate the file. Migration, if
it ever exists, is a core tool (`persia` CLI, ROADMAP 10.4), not a background step inside `Open`.

Golden fixtures under `tests/fixtures/format/v<major>.<minor>/` stay the core's tests (SPEC §15). The
bindings do not copy them. One conformance scenario opens a fixture the core already wrote, once such a
fixture is a database rather than a header. Today the fixtures are format primitives, not databases.

## Compatibility matrix

Published with the first binding release, as `docs/sdk/COMPATIBILITY.md` (created then, not in this
design). Rows look like:

| Package | Core revision | ABI | Format majors it can read | Format majors it will write |
|---|---|---|---|---|
| `@persiadb/node` 0.1.0-alpha.0 | `v0.1.0-alpha` | 0.1 | 1 | 1 |
| `sdk/persia` v0.1.0-alpha.0 | same | 0.1 | 1 | 1 |

Until v1.0 the honest content of that table is "this package opens files written by the core revision
it was built with, and by nothing else we are willing to promise." A newer package may read an older
pre-1.0 file only when the core it links still can. SPEC §15 already says a released format version is
frozen and an unreleased one may change in place. Pre-alpha tags are not that freeze. ROADMAP 10.5.2
requires the `v0.1.0-alpha` tag to say the format is unstable. The SDK tags repeat that sentence in
their release notes.

Network-client compatibility (SDK ↔ server, ROADMAP 14.4) is a different matrix. Do not merge the rows.

## Go module

Module `github.com/tomiok/persiaDB/sdk/persia`, package `persia`, directory `sdk/persia`.
The last element of the import path is the package name, so callers write `persia.Open` without an alias.

### What `go build` does

1. cgo is required (`CGO_ENABLED=1`). Pure Go builds fail with a clear `#cgo` error that points at this
   document, not with a missing-symbol error from the linker.
2. If `PERSIA_LIB_DIR` is set, use `libpersia.a` and `persia.h` from that directory. This is the offline
   and the source-build path.
3. Otherwise download the release asset for `${GOOS}_${GOARCH}` whose version equals the module
   version, verify the checksum committed in the module (`checksums.txt`), and cache it under the Go
   build cache. The URL is the GitHub release for that module tag. The checksum file is reviewed in the
   same pull request as the version bump.
4. Link the static library. The link line (extra system libs, libunwind, `-pthread`) is recorded per
   target in a small cgo file generated by the release job and committed. It is not guessed in
   application code.

A source build, for contributors and for targets without a prebuilt:

```bash
# from a persiaDB checkout, once persia-ffi exists
cargo build -p persia-ffi --release
export PERSIA_LIB_DIR=$PWD/target/release
cd sdk/persia && go test ./...
```

There is no `//go:generate` that invokes `cargo` on a normal `go build`. People who depend on the
module should not need a Rust toolchain (the same zero-friction rule ADR-0003 applies to `protoc`).

### First prebuilt matrix

| GOOS | GOARCH | Rust target | Notes |
|---|---|---|---|
| linux | amd64 | `x86_64-unknown-linux-gnu` | glibc, the default Go target |
| linux | arm64 | `aarch64-unknown-linux-gnu` | glibc |
| darwin | amd64 | `x86_64-apple-darwin` | |
| darwin | arm64 | `aarch64-apple-darwin` | |
| windows | amd64 | `x86_64-pc-windows-gnu` | mingw, which is what Go's cgo uses when `gcc` is on `PATH` |

Not in the first matrix: linux musl, windows arm64, android, ios, freebsd. musl is the first addition
after the gnu build is boring, because Alpine is common and because a gnu staticlib linked into a musl
cgo binary is a support incident. The package docs will say "Alpine: not yet" rather than fail at
runtime inside `Open`.

The static library is large (Rust runtime plus zstd). It is a release asset, not a file committed to
the git module. `go get` of the module fetches sources of a few hundred kilobytes; the first `go build`
fetches the library. Builds with `PERSIA_LIB_DIR` set do not fetch it.

Supply chain (SPEC §17): checksums in the module, assets named with the version, the release workflow
builds them from the tag rather than uploading a developer's laptop. The same tag builds the npm
binaries.

### Windows

mingw and the Go race detector, and mingw and Rust's unwinder, are the risk. The first Windows job
runs `go test` of the conformance adapter with the prebuilt staticlib. If unwind across the cgo
boundary corrupts the Go stack on a forced panic, `PERSIA_PANIC` is still the contract and the bug is
fixed before publish. Shipping a known-bad panic path is worse than slipping the Windows asset.

## npm

`@persiadb/node` is a JavaScript package whose `optionalDependencies` are the platform packages listed
in [typescript.md](./typescript.md). napi-rs is the build system. Each platform package contains one
`.node` file and declares `os` and `cpu` so npm selects it.

Users run `npm install @persiadb/node`. They do not run node-gyp, cmake, or cargo. A platform with no
prebuilt fails install of that optional package and the entry point throws an error that names the
missing target, before any call to `open`.

The Node package links the `persia-ffi` rlib into the `.node` file. It does not download
`libpersia.a`. The Go and Node binaries are built from the same commit and the same safe Rust API, and
they are different files. That is deliberate (ADR-0018): Go wants a staticlib, Node wants a `.node`.

### First prebuilt matrix

| Package suffix | Target |
|---|---|
| `linux-x64-gnu` | Node on glibc |
| `linux-arm64-gnu` | |
| `linux-x64-musl` | Alpine. Included for Node because napi-rs already cross-compiles it and Node-on-Alpine is common. The Go module does not promise musl in the same release. |
| `darwin-x64` | |
| `darwin-arm64` | |
| `win32-x64-msvc` | Node's usual Windows ABI. This is MSVC, not the mingw staticlib Go uses. Two Windows artifacts, one source. |

Node 20 and Node 22 are the versions the N-API header is built against (Node-API is stable across
them; the CI still runs both). Bun and Deno are smoke-tested. A failure on Bun or Deno blocks the
release if it is a load failure of the `.node` file, and is recorded as a gap only when the runtime
itself rejects N-API.

## Release process

One core tag, then the bindings. Never the other way around: the bindings have nothing to wrap.

1. Tag the core, currently planned as `v0.1.0-alpha` with an explicit "format unstable" notice
   (ROADMAP 10.5.2). The core is not published to crates.io until its own release-engineering leaf
   (10.5.1) says so. The bindings do not require the core to be on crates.io; they build from the git tag.
2. CI on that tag builds `persia-ffi` staticlibs and the `.node` packages. The workflow lives in
   `.github/workflows/` next to the existing CI. It does not run on every pull request of the core:
   a docs change or a format-crate change does not need six cross compilers. It runs on tags, on
   workflow dispatch, and on pull requests that touch `crates/persia-ffi/**`, `sdk/persia/**`, or
   `sdk/node/**`.
3. Conformance (below) runs against those artifacts on linux amd64 at least, and on one macOS and one
   Windows runner for the smoke subset.
4. Publish GitHub release assets: staticlibs, checksums, header. Publish npm platform packages first,
   then `@persiadb/node`, with provenance. Publish the Go module by tagging
   `sdk/persia/vX.Y.Z` (Go's submodule tag convention).
5. Append a row to the compatibility table and a CHANGELOG entry under the SDK heading.

The Apache-2.0 license of the repository covers the bindings. Third-party notices for zstd and the
other allowed crates travel with the release archive, the way a static binary has to. `cargo deny`
still applies to `persia-ffi` because it is a workspace member. `sdk/node`'s npm dependencies are
reviewed when they are added; napi-rs is the expected one, and it is justified in that implementation
PR against ADR-0001's allowed list (it is not a dependency of the workspace).

No SDK release happens while the core version is `0.0.0` and `publish = false` without a tag. A
design merge does not publish anything.

## Tests

The core keeps the tests it already requires: property tests, golden files, fuzz, differential tests
against the reference model, crash injection (SPEC §16.1). The bindings do not re-prove fsync. They
prove the wrapper matches the core.

### Shared conformance

ROADMAP 14.1 specifies a language-neutral YAML suite for the **network** clients. The embedded bindings
should use that shape so a scenario is written once. 14.1 is not written yet. When it is, add a
`transport` field:

```yaml
# ILLUSTRATIVE. Not a file in the tree. Settle the schema with ROADMAP 14.1.1.
name: typo-returns-the-correction
transport: [embedded, grpc]   # grpc runs only when the server exists
setup:
  - create_collection: { name: products, schema: products.json }
  - put: { collection: products, doc: { id: sku-1, title: running shoes } }
  - commit: { collection: products }
call:
  search: { collection: products, q: runing }
expect:
  error: null
  hit_ids: [sku-1]
  relaxation:
    level: fuzzy
    corrected: { runing: running }
```

Embedded-only scenarios omit `grpc`. Server-only scenarios (auth, `min_seq` against a replica) omit
`embedded`. The runner for a binding is a small adapter (ROADMAP 14.1.3's idea, implemented per
language):

| Adapter | Calls | When it can exist |
|---|---|---|
| Rust | `persia::Db` directly | M10 |
| C | `persia_*` in-process | the `persia-ffi` crate |
| Go | the `persia` package | `sdk/persia` |
| TypeScript | `@persiadb/node` | `sdk/node` |
| gRPC | the network clients | M14, not this design |

Assertions on scores use the epsilon SPEC §7.2 says the reference model comparison must document.
That epsilon is not a number in the SPEC yet. The suite does not invent `1e-6`. Until the core
publishes it, conformance checks hit ids, order, relaxation level, corrected terms, error codes, and
`manifest_seq` monotonicity, and leaves score equality to the Rust differential tests.

Scenarios to write first, matching ROADMAP 14.1.2 where it applies to a local file:

- Create collection, put, get, delete, get misses.
- Upsert changes the stored field.
- Search with a filter and a facet.
- Typo query returns the relaxation object (SPEC §7.6), and `relax: false` returns empty.
- Read-your-writes: put, search in another goroutine or another call, then commit, reopen, search.
- Second writer: `ErrConflict` / `"conflict"`.
- Close with an open collection: busy.
- Corrupt file: copy a fixture, flip a byte, open, expect `corrupt` and a live process.
- Unsupported major: a header with `format_major` bumped, expect `unsupported`.

Crash-injection and `kill -9` stay in `persia-storage` and, later, the engine. The binding suite's
durability check is the reopen-after-commit scenario, which is enough to catch a wrapper that forgot
to call `commit` or closed without dropping the lock.

### Per language

Go, on every PR that touches the module, and on the release workflow:

- `go test ./...`
- `go test -race ./...`
- `go vet`
- `staticcheck` (the same tools ROADMAP 14.3.6 already asks of the network client)

TypeScript:

- The package's test runner (node:test is enough; vitest is not required) against the local `.node`
  build.
- Typecheck with `tsc --noEmit`.
- The conformance adapter.
- A load smoke: one Node process, several readers, one writer goroutine's worth of puts. Not a
  benchmark. Benchmarks stay in the core (SPEC §16.3, ROADMAP 15.1).

C ABI, inside the workspace, so `cargo test` covers them:

- Null pointers, zero lengths, and non-UTF-8 return `invalid` and do not panic.
- A test-only hook that panics inside `api` returns `PERSIA_PANIC`, poisons the handle, and `close`
  still succeeds.
- A fuzz target once the exports parse caller bytes (JSON documents, queries, paths). Hostile input
  must not panic and must not abort (SPEC §17, CLAUDE.md). The fuzz target lives under `fuzz/` like
  the other parsers. It is added with the crate, not with this design.
- Leak check in debug: every `persia_bytes` from a successful `get` and `search` is freed, asserted
  with an allocation counter in `cfg(test)`.

Differential check, release workflow: the same operations against one file through Rust and through
the binding. Hit ids and relaxation match. This is the check that catches a JSON field renamed in
only one package.

### What CI of this repository does with this design

This pull request adds markdown. It does not add a crate, so `cargo xtask check-deps` is unchanged and
no new workflow runs. The existing PR checks (fmt, clippy, tests, website build when `website/**`
changes) are the gate.

## Docs and examples

When the packages exist, not before:

| Place | Content |
|---|---|
| godoc on the Go package | The walkthrough from [go.md](./go.md), kept as a runnable example under `sdk/persia/example_test.go` so `go test` compiles it |
| npm readme and the generated TypeScript docs | The walkthrough from [typescript.md](./typescript.md) |
| `examples/go/` and `examples/node/` in this repository | Products search, including a typo and the relaxation printout. Parallel to the Rust examples ROADMAP 10.3.2 asks for (`quickstart`, `products-search`, `blobs`, `relaxation demo`) |
| Website guide | The Embedded SDKs page stays the short version and links here. Snippets on the website are updated to match the shipped API, and keep the pre-alpha banner until a release exists |

Examples that cannot run are worse than no examples. They land in the same release as the binding, and
CI runs them (`go test` on the example, `node examples/node/quickstart.mjs` against a temp file).

The illustrative snippets in `docs/sdk/` are the spec of those examples. If a snippet and the shipped
API disagree, the snippet is a bug in this directory, unless the SPEC changed and the snippet was
updated to match.

## Implementation leaves, when it is time

Do not file these against M14. M14 is the gRPC clients. A reasonable split, once M10.1 has types to
wrap:

- `persia-ffi` crate, header, xtask generator, panic and null tests, `ALLOWED` and `UNSAFE_ALLOWED` updates.
- Go module (`sdk/persia`), cgo wrapper, prebuilt download, race tests.
- napi package, platform builds, TypeScript types.
- Conformance adapter for the three embedded runners, sharing scenarios with 14.1.
- Release workflow and the compatibility table.

Each of those is one leaf and one pull request, with tests, in the usual way. This design is the brief
for them. It is not one of them.
