# ADR-0018: Embedded Go and TypeScript bindings share one C ABI

- Status: proposed
- Date: 2026-10-17
- Related: SPEC §1.1, §3, §8.4, §13, §15; ADR-0001, ADR-0003, ADR-0010, ADR-0017; ROADMAP M10, M14

## Context

Persia is an embedded database: `Db::open` on a file, no daemon (SPEC §1.1, §14). The public Rust crate that
will expose `Db` and `Collection` is still a stub — [`crates/persia/src/lib.rs`](../../crates/persia/src/lib.rs)
exports no types — and the first release that is supposed to is `v0.1` (ROADMAP M10), blocked on the write
path, query, relaxation, and blobs.

SPEC §13 and ROADMAP M14 already name two **network** clients, `sdk/rust` (`persia-client`) and `sdk/go`
(`persia-go`), which speak gRPC to `persia-server`. Those do not help a Go or TypeScript program that wants
the embedded pillar: open `app.persia` in-process, the way the Rust API will. The owner asked for that second
surface, for everyday Go and TypeScript developers, including a binding strategy.

The engine is written once, in this repository (ADR-0001). Durability is fsync, an exclusive writer lock, and
(optionally) memory-mapped reads of committed frames (SPEC §4.5, §4.7, §8.4; ADR-0010, ADR-0016, ADR-0017).
A second implementation, or a host that cannot make those calls, would be a different database.

The workspace forbids `build.rs` and generates code with `cargo xtask` (ADR-0003). `unsafe` is allowed only
in modules an ADR names (`xtask/src/repo_checks.rs`, `UNSAFE_ALLOWED`). Nothing in this ADR adds a crate, a
dependency, or an `unsafe` block; it reserves the shape so the later implementation does not re-litigate it.

The design that follows from this decision lives in [`docs/sdk/`](../sdk/README.md).

## Decision

1. **Two SDK products.** Embedded bindings and the M14 network clients are different libraries and stay on
   different paths.
   - Network, unchanged: `sdk/rust` (`persia-client`), `sdk/go` (module `persia-go`). SPEC §13.2, ROADMAP M14.
   - Embedded, not created yet: `crates/persia-ffi` (C ABI), `sdk/persia` (module
     `github.com/tomiok/persiaDB/sdk/persia`, Go package `persia`), `sdk/node` (npm package
     `@persiadb/node`). A later browser/edge build, if it happens, is `sdk/wasm` (`@persiadb/wasm`).
   - Published names (`@persiadb/*`) are the ones to confirm before the first publish. The directory layout
     is the decision that matters now.
2. **One engine.** Go and TypeScript call the Rust core. They do not reimplement segments, the WAL, scoring,
   or relaxation. A file written by the Rust API, the Go binding, or the TypeScript binding is the same file
   (SPEC §15). The bindings add no on-disk bytes.
3. **Go uses cgo over a C ABI.** `persia-ffi` is a workspace crate with crate types `lib`, `staticlib`, and
   `cdylib`. Go links the static library and calls the C functions. Prebuilt static libraries per
   OS/architecture are how a Go developer builds without a Rust toolchain; a source build remains available.
   Pure Go and WASM-in-Go (wazero) are rejected for the reason in Alternatives.
4. **TypeScript uses N-API first, WASM later.** The first package is an N-API addon (napi-rs) for Node.js,
   Bun, and Deno. It links the `persia-ffi` rlib and calls the same safe Rust functions the C exports call, so
   there is one marshalling of documents and one set of error codes. WASM for the browser and for edge
   isolates is a second package, built only after a `Storage` backend exists that does not need mmap or POSIX
   fsync. It is not part of the first SDK release.
5. **The C ABI is the contract; the rlib is the implementation.** Operation names, ownership, error codes, and
   the JSON documents cross both languages are specified in [`docs/sdk/c-abi.md`](../sdk/c-abi.md). C exports
   are thin wrappers. The header `crates/persia-ffi/include/persia.h` is generated by a future
   `cargo xtask ffi-header` and committed. No `build.rs` (ADR-0003). cbindgen, when it is added, is a tooling
   dependency of `xtask` only.
6. **`unsafe` stays in one module.** `persia-ffi` will use `#![deny(unsafe_code)]` at the crate root, with
   `unsafe` allowed only in its C-export module, which must be added to `UNSAFE_ALLOWED` in the same change.
   Every block gets a `// SAFETY:` comment. The safe Rust API of the crate does not use `unsafe`. Every C
   export catches panics (`catch_unwind`) and returns an error; the crate must not be built with
   `panic = "abort"`. A panic poisons that database handle. A mapped-page fault (`SIGBUS` /
   `EXCEPTION_IN_PAGE_ERROR`, ADR-0010) is not a panic and still ends the process. The bindings do not invent
   a softer rule.
7. **Foreign calls borrow caller memory for the call only.** The engine copies what it must keep. Returned
   buffers are allocated by Rust and freed by a `persia_*_free` function, never by the host allocator. No
   callback from Rust into Go or JavaScript in the first ABI, so a host pointer is never stored and the cgo
   pointer rules stay simple. Search returns one page (SPEC §7.4); it does not hand back a live iterator.
8. **Documents and queries cross the boundary as UTF-8 JSON**, in the shapes SPEC §6.2, §6.4, and §7.1
   already sketch. Go structs and TypeScript values are serialized by the language package. The Rust
   `put_struct` path (ROADMAP 10.1.4) stays inside the Rust crate; the FFI does not grow generics.
9. **Nothing is published before the core has a release.** The first binding release follows the v1.0 tag
   (ROADMAP M15, then M16). ROADMAP 10.5.2's `v0.1.0-alpha` tag says the format is unstable; that tag is the
   core's notice, not the binding cut. Until format v1.0 there is no compatibility promise across core
   versions (SPEC §15), and the ABI major may break on each pre-1.0 release. Three numbers stay distinct:
   file format, C ABI, language-package semver. See [`docs/sdk/distribution.md`](../sdk/distribution.md).
10. **Binding leaves are M16.** M14 stays the network clients. The browser and edge package is M28, after a
    portable `Storage` backend. This decision does not restate those leaves.

`persia-ffi`, when it is added, depends only on `persia`. That edge is recorded in `ALLOWED`
(`xtask/src/check_deps.rs`) in the same pull request as the crate. `sdk/node` stays **outside** the Cargo
workspace so napi's build script does not enter a workspace that forbids `build.rs`.

## Consequences

- A Go or TypeScript program links the real engine: one file format, one crash story, one relaxation cascade.
- cgo is part of the Go build. Cross-compilation and a missing C compiler are the cost. Prebuilt static
  libraries and a documented source-build tag are the mitigation, not a second engine.
- CI gains, later, a matrix that produces those libraries and the per-platform `.node` packages. Users of the
  embedded engine do not run that matrix.
- Host processes inherit ADR-0010: a fault on a mapped page kills the process, Go runtime and libuv included.
  Callers who cannot accept that use the core's ordinary reads, once `Db::open` exposes the choice the
  container already has (`enable_mapped_reads` is opt-in; pread is the default, ADR-0017).
- The C ABI will need `unsafe` and, later, cbindgen on the allowed list. Both are justified here so the
  implementation PR only has to add them, not re-argue them.
- TypeScript in the browser is explicitly out of the first release. Edge and browser hosts need the
  portable storage backend M28 builds.
- SPEC §1.1 and §13 now distinguish the two SDK products. The embedded API they wrap still does not exist.

## Alternatives considered

- **Pure Go, reimplementing the engine.** Rejected. It forks the product ADR-0001 exists to prevent: a second
  segment writer, a second WAL, a second BM25F, and a permanent risk that the two disagree on crash recovery.
  File-format compatibility (SPEC §15) would depend on two codebases staying in lockstep.
- **Go via WASM (wazero).** Rejected as the primary binding. The local commit protocol is `fdatasync` and an
  exclusive lock (SPEC §4.5, §8.4). Mapped reads are part of the storage crate today (ADR-0017). WASI does not
  offer that contract, and a search engine running inside wazero gives up the mmap path and any later SIMD
  (ROADMAP 15.2.1) for a host that still could have linked the native library. A no-cgo WASM build can be
  revisited if a portable `Storage` backend exists and someone needs hosts that forbid cgo. It is not the SDK.
- **TypeScript as WASM only.** Rejected for servers. Node, Bun, and Deno can load a native addon and then get
  the same file, the same lock, and the same fsync as Rust. A WASM-only SDK would make the common case (a
  server opening a file) pay for a sandbox aimed at browsers.
- **N-API with no WASM follow-up.** Rejected as a permanent rule. Browser and edge are real TypeScript
  deployments. They are deferred, not forbidden. They wait on storage, not on a second API design.
- **One shared library, `dlopen`'d by both Go (purego) and Node.** Rejected for the first release. purego
  avoids cgo but cannot statically link, so the database stops being a single binary. ffi-napi-style loading
  of a cdylib from Node is a second, less maintained marshalling layer. napi-rs linking the rlib, and cgo
  linking the staticlib, produce two artifacts from one Rust API. That is the trade we take.
- **Making the network client the only Go SDK, and telling embedded users to run `persia-server`.** Rejected.
  It drops the zero-friction pillar for every non-Rust caller, and the server does not exist either (M11).
  The network clients remain the right answer for a remote cluster (M13, M14).
- **Putting the embedded Go module at `sdk/go`.** Rejected. SPEC §13.2 and ROADMAP 14.3 already assign that
  path to the gRPC client. Reusing it would make the two products impossible to tell apart in import paths.
